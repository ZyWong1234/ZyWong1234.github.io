Project Overview

Moon and Bloom is a boutique florist selling seasonal arrangements and balloon displays. The brief was a storefront that looks the part, but the real requirement was operational: the owner had to be able to run the catalogue themselves, without a developer in the loop every time a flower sells out or a price changes.

So the site is two applications sharing one codebase. The public half is a fast, SEO-focused marketing site — collection pages, individual flower and balloon pages, an about page and an enquiry form. The private half is an admin backoffice at /admin where the florist manages flowers, photographs, categories, shop details and incoming enquiries.

Payments were deliberately left out of scope. Rather than bolt on a checkout the shop was not ready to operate, the database schema keeps the seams open — price_cents and stripe_price_id already exist — so a checkout can be added later without a rewrite. Scoping that decision explicitly kept the first release small enough to actually ship.

Key Features

Public storefront

Home, flowers, balloons, about and contact pages, with individual pages per item generated from the database rather than hand-written.

Admin backoffice

The florist manages flowers, images, categories, shop details and enquiries from a private dashboard — no developer involvement needed.

Custom balloon designer

A guided enquiry flow capturing occasion, colour scheme, quantity, date and budget, so a bespoke request arrives with everything already answered.

Role-based staff accounts

Superadmin and admin roles with no public sign-up. Every admin route is guarded server-side, so a new admin page is private by default.

SEO built in

Per-page canonical URLs and Open Graph tags, Florist and Product JSON-LD structured data, and a sitemap generated live from available stock.

Edge deployment

Runs on Cloudflare Workers with D1 for data and R2 for images. Pushing to main triggers a build and deploy automatically.

Engineering Decisions

  • Deploys are a git push. Pushing to main triggers a Cloudflare Workers build. Deploying from a laptop was deliberately retired, because it uploads uncommitted working-directory changes and silently drifts the live site away from main.
  • Migrations are not automatic. A generated SQLite migration can rebuild a whole table, which is not something that should fire on every push, so schema changes are applied deliberately and before the code depending on them ships.
  • Authorization lives in one place. Route guards run in server hooks with the rules in a single authz module, so access is decided once rather than re-implemented per page.
  • Secrets are stored as Worker secrets, not dashboard variables — a plain variable added in the dashboard is dropped by the next deploy, since a deploy uploads a complete set of bindings from config.
  • The enquiry forms carry a honeypot field and are rate limited, with authentication events recorded, keeping spam and brute-force attempts off a site with no captcha.

What I Built

I built and shipped this project end to end — design implementation, front end, backend, database, authentication, deployment and the operational documentation the shop runs on.

  • Built the public storefront in SvelteKit with Svelte 5 runes and Tailwind CSS v4.
  • Designed the Drizzle schema covering flowers, images, categories, shop details, enquiries, rate limiting and authentication events.
  • Implemented the admin backoffice for catalogue, media, category, shop-detail and enquiry management.
  • Set up authentication with better-auth, including role-based guards, a one-time bootstrap route for the first account, and superadmin-managed accounts thereafter.
  • Built image upload and delivery through Cloudflare R2, served via a dedicated route.
  • Implemented the SEO layer: per-page metadata, JSON-LD structured data, and a sitemap generated from live availability.
  • Configured deployment on Cloudflare Workers with D1 and R2 bindings, and continuous deployment from GitHub.
